### README

#### 1. Введение
Для решения задания рассматриваются две архитектуры: монолитная и с использованием микросервисов.
Архитектура разделена на несколько доменов: users, catalog, orders, payments, recommendations и notifications.

#### 2. Микросервисный подход
В микросервисном подходе каждому домену сопоставлен микросервис. Внутри каждого микросервиса заведем свою базу данных
для скрытия информации и соблюдения границ. Таким образом users владеет информацией о пользователях, catalog о товарах,
orders о заказах, payments о платежах, а recommendations о статистике пользователей для формирования ленты. Заметим, что
таким образом получается небольшой coupling, потому что методы из одного микросервиса дергают мало других. Получается,
при поддержке продукта не придется думать о лишних зависимостях. Минус заключается в том, что нужно тратить
ресурсы на взаимодействие между компонентами. Это можно реализовать, например, с помощью RPC подхода или HTTP.

#### 3. Монолоитный подход

В монолитном подходе домены остаются разделенными внутри приложения, но масштабируются как единое целое, а также
все сконцентрированно в одной БД. Это может быть удобно для небольшого проекта, потому что меньше компонент и не
надо работать с сетью. Однако а таком случае в единственном модуле получается маленький cohesion. Кроме того, отсутствуют
границы и скрытие даннх, что приводит к тому, что при развитии кодовой базы одного домена, приходится думать о других.

#### 4. Trade-off

Trade-off очевиден, чтобы работать с микросервисами, нужно потратить время на общение между компонентами, но поддерживать большой
проект намного удобнее. В слуаче с монолитом, не нужно думать о сети, однако имеет место увеличение связанности и сложности изменений по мере роста кодовой базы. Значит,
микросервисы лучше подходят для больших проектов в долгую, а монолит для компактных или тестовых. В случае с интернет магазином,
явно выигрывет микросервисная архитектура.
